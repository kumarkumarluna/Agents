# 🧠 What Is a Tool Registry?

A **Tool Registry** is a central component that stores information about available tools.

In this implementation, each registered tool contains:

```python
{
    "function": function,
    "schema": schema
}
```

For example:

```python
registry.register(
    "calculator",
    calculator,
    calculator_schema
)
```

The registry therefore connects:

```text
Tool Name
    ↓
Tool Registry
    ├── Function
    └── Schema
```

When the LLM requests a tool by name, the agent can use the registry to dynamically locate the corresponding Python function.

---

# 🔄 Before Tool Registry

Previously, the agent used hard-coded conditional logic:

```python
if tool_name == "calculator":
    result = calculator(
        arguments["a"],
        arguments["b"],
        arguments["operation"]
    )

elif tool_name == "get_weather":
    result = get_weather(
        arguments["city"]
    )

elif tool_name == "get_time":
    result = get_time()

else:
    result = "Unknown tool"
```

This works, but it becomes difficult to maintain as the number of tools increases.

If the agent has many tools, the execution logic can become a large collection of `if/elif` statements.

---

# 🚀 After Tool Registry

The tool functions are registered centrally:

```python
registry = ToolRegistry()

registry.register("calculator", calculator, calculator_schema)
registry.register("get_weather", get_weather, get_weather_schema)
registry.register("get_time", get_time, get_time_schema)
```

When the LLM requests a tool:

```python
tool_name = tool_call.function.name
```

The registry dynamically finds the registered tool:

```python
tool = registry.get(tool_name)
```

The function is then extracted:

```python
tool_function = tool["function"]
```

And executed using the arguments generated by the LLM:

```python
result = tool_function(**arguments)
```

There is no need for another `elif` when a new tool is added to the registry.

# 🔍 How Dynamic Tool Execution Works

Suppose the LLM requests:

```python
tool_name = "calculator"
```

The agent performs:

```python
tool = registry.get("calculator")
```

The registry returns:

```python
{
    "function": calculator,
    "schema": calculator_schema
}
```

The agent extracts the function:

```python
tool_function = tool["function"]
```

Suppose the LLM provides:

```python
arguments = {
    "a": 25,
    "b": 40,
    "operation": "multiply"
}
```

The agent executes:

```python
tool_function(**arguments)
```

This is equivalent to:

```python
calculator(
    a=25,
    b=40,
    operation="multiply"
)
```

The calculator returns:

```text
1000
```

# 🧩 Tool Schema vs Tool Function vs Tool Registry

These three concepts must not be confused.

## 1. Tool Schema

The **tool schema** tells the LLM what a tool is and how to call it.

It describes:

- Tool name
- Tool purpose
- Parameters
- Parameter types
- Required arguments

For example:

```python
calculator_schema = {
    "type": "function",
    "function": {
        "name": "calculator",
        "description": "Perform basic arithmetic calculations.",
        "parameters": {
            "type": "object",
            "properties": {
                "a": {"type": "number"},
                "b": {"type": "number"},
                "operation": {
                    "type": "string",
                    "enum": [
                        "add",
                        "subtract",
                        "multiply",
                        "divide"
                    ]
                }
            },
            "required": ["a", "b", "operation"]
        }
    }
}
```

The LLM uses this information to decide:

```text
Which tool should I call?
What arguments should I provide?
```

## 2. Tool Function

The **tool function** is the actual Python code that performs the operation.

Examples:

```python
calculator(...)
get_weather(...)
get_time(...)
```

## 3. Tool Registry

The **ToolRegistry** connects the tool name with both the function and its schema.

Conceptually:

```text
"calculator"
      │
      ├── calculator function
      │
      └── calculator schema
```

Therefore:

```text
Tool Schema
    ↓
Tells the LLM WHAT the tool is

Tool Registry
    ↓
Connects the tool name to its implementation

Tool Function
    ↓
Actually executes the operation
```

# 🏗️ ToolRegistry Implementation

The current registry class is:

```python
class ToolRegistry:

    def __init__(self):
        self.tools = {}

    def register(self, name, function, schema):
        self.tools[name] = {
            "function": function,
            "schema": schema
        }

    def get(self, name):
        return self.tools.get(name)
```

The important part is:

```python
self.tools[name] = {
    "function": function,
    "schema": schema
}
```

This allows one tool name to be associated with both:

- the executable Python function
- the schema supplied to the LLM

# ➕ Adding a New Tool

Suppose a new `search` tool is created:

```python
from tools.search import search
```

Create its schema and register it:

```python
registry.register(
    "search",
    search,
```

The registry handles the lookup dynamically.

This is the main scalability advantage of the registry pattern.

# 🛡️ Handling Unknown Tools

The registry also provides a way to handle an invalid tool name:

```python
tool = registry.get(tool_name)

if tool is None:
    result = "Unknown tool"
else:
    tool_function = tool["function"]
    result = tool_function(**arguments)
```

For example:

```text
LLM requests:
"send_email"
       ↓
Registry lookup
       ↓
No matching tool
       ↓
"Unknown tool"
```

This prevents the agent from attempting to execute a function that is not registered.

# 🧠 Why Tool Registry Matters

Without a registry:

```text
Tool 1 → if
Tool 2 → elif
Tool 3 → elif
Tool 4 → elif
Tool 5 → elif
...
```

With a registry:

```text
Tool Name
    │
    ▼
Tool Registry
    │
    ▼
Python Function
```

The registry separates:

1. What tool the LLM requested
2. Which Python function implements that tool
3. How that function is executed

This makes the execution layer easier to extend and maintain.

---

# 🛡️ Agent Loop Safety

The agent loop uses a maximum iteration limit:

```python
max_iterations = 10

for iteration in range(max_iterations):
    ...
```

This is safer than blindly using:

```python
while True:
    ...
```

A maximum iteration limit prevents an unexpected model/tool-calling loop from continuing indefinitely and consuming unnecessary API calls.

If the limit is reached:

```text
Agent stopped: maximum iterations reached.
```

# ▶️ Running the Agent

## 1. Install Dependencies

Synchronize the project environment using `uv`:

```bash
uv sync
```

## 2. Configure Environment Variables

Create a `.env` file:

```env
GROQ_API_KEY=your_api_key_here
```

Do not commit the `.env` file.

## 3. Run the Agent

```bash
uv run python Main_folder/agent_loop.py
```

The agent will:

1. Send the user request to the LLM.
2. Provide the registered tool schemas to the LLM.
3. Allow the LLM to select a tool.
4. Extract the requested tool name.
5. Look up the tool in the registry.
6. Extract the Python function.
7. Execute the function with the generated arguments.
8. Send the tool result back to the LLM.
9. Continue the agent loop.
10. Stop when the LLM produces a final answer or the iteration limit is reached.

# ⭐ Key Takeaway

A Tool Registry is a simple architectural pattern, but it solves an important problem:

```text
Hard-coded dispatch logic
          ↓
     Tool Registry
          ↓
 Dynamic tool execution
```

Instead of teaching the agent loop how to execute every individual tool, the registry provides a **central mapping between tool names, schemas, and executable Python functions**.

That makes the system easier to extend, maintain, and reason about as the number of tools grows.
